## 场景 1：简单安装任务（workflow 创建 + 验证 + 汇报）

**目的**：验证 ≥3 步任务自动创建 workflow，步骤推进正常，最终汇报到正确来源。

**操作**：
1. Web 聊天发送：`帮我安装 jq 和 curl，装完验证一下版本`
2. 等待任务完成

**预期**：
- [ ] 创建 workflow，步骤 ≥ 3（检查环境 / 安装 / 验证）
- [ ] 每个步骤按顺序推进，前一完成后一才开始
- [ ] 验证步骤有真实命令输出作为证据
- [ ] 最终汇报消息包含版本号
- [ ] workflow 状态变为 completed
- [ ] 无重复 job（同命令不跑两次）
- [ ] 步骤 attempts 合理（≤3，非每个子操作都算）

**检查命令**：
```bash
# 查 workflow 状态
docker exec -w /app/backend termman-backend-1 python -c "
from app.services.agent.task_workflow import task_workflow_manager
wfs = task_workflow_manager.list_active(item_id='ea52de0c-51b7-4b49-a43d-985ed2e09579')
for w in wfs: print(w.id, w.status, w.title)
"
```

## 场景 2：复杂任务故障恢复（外网失败 → 换源/降并行）

**目的**：验证任务失败时 agent 能诊断原因、插入 recovery step、不陷入死循环。

**操作**：
1. Web 聊天发送：`帮我从源码编译安装 Python 3.12，装完验证 python3.12 --version`
2. 观察编译过程（可能 OOM/超时）
3. 如果失败，观察 agent 是否自动插入 recovery step

**预期**：
- [ ] 创建 workflow，步骤包含：检查环境 / 安装依赖 / 下载源码 / 编译 / 验证
- [ ] 编译失败时（SIGTERM/OOM），agent 诊断原因（如并行度过高）
- [ ] 自动 insert_recovery_step（如 `make -j2`），不卡住等用户
- [ ] recovery step 创建后 agent 立即继续执行，不需要用户发"继续"
- [ ] 策略切换 ≤ 2 次（不反复 APT→tarball→GitHub→APT）
- [ ] 最终验证通过或明确报告失败原因
- [ ] 总 job 数 ≤ 10（不膨胀）

**超时处理**：
- 编译 job 可能跑 300s+，属正常
- 如果 job 超时被 kill（exit -15），agent 应识别并调整策略

## 场景 3：中途取消任务（job + workflow 清理）

**目的**：验证用户中途取消时，running jobs 被终止，workflow 正确标记 cancelled。

**操作**：
1. Web 聊天发送：`帮我安装 openjdk-21-jdk-headless，装完验证 java -version`
2. 等 agent 开始执行（出现 running job）
3. 发送：`算了不装了，取消吧`
4. 观察清理行为

**预期**：
- [ ] 取消指令被识别，workflow 状态变为 cancelled
- [ ] 所有 running jobs 被终止（cancel 调用）
- [ ] 取消确认消息发送给用户
- [ ] 取消后发闲聊不再触发 workflow 更新
- [ ] 从新轮次取消也能成功（ticket 回退到 item 级查找）

**二次验证**：
- 取消后再发 `帮我装个 cowsay`，应创建新 workflow，不受旧任务影响

## 场景 4：三通道简单聊天（不建 workflow、不纠缠）

**目的**：验证简单问答不触发 workflow，各通道回复到正确来源。

**操作**：
1. **Web 聊天**：发送 `1+1等于几`
2. **QQ 模拟**（dispatch API）：发送 `你好呀`
3. **终端模拟**：发送 MC 格式 `<Steve> 服务器几个人在线`

**预期**：
- [ ] Web：直接回复 "2"，不创建 workflow，不调 update_task_workflow
- [ ] QQ：回复到 QQ（return_source = qq），不创建 workflow
- [ ] 终端：识别为玩家提问，执行 `list` 命令，回复到终端
- [ ] 三个通道互不干扰，ticket 指向正确
- [ ] 无 "本回合实际工具调用: N 次" 泄露给用户

**QQ 模拟脚本**：
```python
import requests
from app.core.config import settings
BASE = "http://127.0.0.1:8000"
secret = settings.ROBOT_BRIDGE_SHARED_SECRET or settings.SECRET_KEY
robot_id = "5cbc7f55-04a2-40f6-900a-05e0b0dd652a"
payload = {
    "sender_key": "private_2537134688",
    "text": "你好呀",
    "reply_target": {
        "target_type": "private",
        "target_id": "2537134688",
        "metadata": {"sender_name": "FLY", "sender_id": "2537134688", "conversation_type": "private"}
    }
}
r = requests.post(f"{BASE}/api/v1/robots/{robot_id}/dispatch", json=payload,
                  headers={"X-Termman-Bridge-Token": secret}, timeout=90)
print(r.status_code, r.text[:200])
```

## 场景 5：任务进行中闲聊不污染 workflow

**目的**：验证活跃任务期间收到无关消息时，workflow 不被污染（不增加 return_targets、不记入步骤证据）。

**操作**：
1. Web 聊天发送：`帮我安装 neofetch，装完跑一下`
2. 等 agent 开始执行（出现第一个 running job）
3. 立即发送：`今天天气怎么样`
4. 等闲聊回复后，继续观察原任务

**预期**：
- [ ] 闲聊被直接回答（或告知正在忙），不调 update_task_workflow
- [ ] workflow 的 return_targets 数量不增加
- [ ] 闲聊内容不出现在步骤证据中
- [ ] 原任务继续正常推进，不因闲聊中断
- [ ] 最终汇报仍发到原始来源（Web chat）
- [ ] 无重复汇报（同一结果不报两次）

**检查方法**：
```bash
# 对比闲聊前后 workflow 的 return_targets 数量
docker exec -w /app/backend termman-backend-1 python -c "
from app.services.agent.task_workflow import task_workflow_manager
wfs = task_workflow_manager.list_active(item_id='ea52de0c-51b7-4b49-a43d-985ed2e09579')
for w in wfs:
    print(f'workflow={w.id[:12]} targets={len(w.return_targets)} steps={len(w.steps)}')
    for s in w.steps:
        print(f'  step {s.order}: {s.title} [{s.status}] attempts={s.attempts}')
"
```
